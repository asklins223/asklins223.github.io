W-02·在职项目·2024.07 – 2025.08·PHP / Swoole / gRPC

英语听说 App 与题库内容平台

两条线一起维护：一条是个人版 App 的功能后端，作业、学习卡、自主练习这些模块要能扛住使用； 另一条是题库内容生产，题型不断新增，题目和试卷要批量进来。AI 能力（口语家教、作文评测） 接在这两条线中间。

模块与微服务

服务是 ThinkPHP + Swoole 起的常驻进程，跨服务调用走 gRPC。我负责的模块包括作业、学习卡、 自主练习，以及后来的 AI 口语家教和 AI 作文评测。Swoole 这一层主要是把长连接、 并发和常驻内存下的资源回收处理干净，不然 PHP 代码里一些「请求结束自然释放」的假设会失效。

AI 能力接入与成本

口语和作文评测要调模型，题库侧还有一类活是批量生成英语近似词——这类任务量大且重复率高， 直接逐条调模型既慢又费 token。做法是用 Coze 搭近似词工作流，配合资源库缓存和批量处理： 命中缓存的直接复用，没命中的攒批处理，重复调用明显降下来。

  • 结果与素材进资源库，同一份内容不重复生成。
  • 批量入口而不是单条入口，减少排队和轮询开销。
  • 评测类接口对超时和异常状态单独处理，避免一次模型抖动拖挂业务请求。

题库内容生产

新增题型是这里的常态工作，一个题型要走完整条链路：数据模型、API、录入页面、再到数据同步。 少一环就会出现「题目录进去了但端上读不出来」。另外教材题目和试卷的批量导入脚本也做过一轮优化， 原来导入一批要人工盯着改格式。

检索与语音

题目检索的压力本来全在 MySQL 上，模糊匹配和多条件筛选一起加就很吃紧， 后来接入 Elasticsearch 把检索分担出去。题目语音用 Azure TTS 生成， 生成结果同样入资源库复用，不每次实时合成。

复用与交付

  • 题目解析逻辑封装成 Composer 公共包，给其他服务复用，避免各处各写一份解析。
  • 接入 OpenTelemetry 与 Jaeger 做链路追踪，跨 gRPC 的服务调用能看清慢在哪一段。
  • 负载均衡走 HAProxy，CI/CD 维护 Jenkins 与 Syncd，交付用 Docker 容器化。
  • 参与过业务统计服务的数据迁移与技术选型讨论。
