AI 原生学习与理解验证系统

大多数笔记工具记录的是「我读过」，而不是「我理解了」。这个项目想做的是后者： 从资料捕获到复习调度走完整条链路，并给 AI 生成的每一个结论加上一道 原文证据门禁——对不上原文的关键点，不允许进入验证环节。

问题

用 LLM 做学习工具有一个很自然的失败方式：它写出一份结构漂亮、读起来很顺、 但和原文其实没有严格对应关系的学习卡。人很难逐句回查，于是错误被存进笔记、 被当作「已掌握」，最后进入复习循环。

所以三条约束从一开始就是硬性的：

  • 可回溯：资料、AI 结论、用户回答、理解状态都要能追到产生它的那个版本。
  • 有证据：AI 结论必须指向原文片段，指不到就降级为待确认。
  • 能验证：理解状态由用户作答推导，而不是由「我看了」自我声明。

闭环设计

流程是 资料捕获 → 学习卡生成 → 原文证据对齐 → 理解验证 → 复习调度。 来源支持 Text、Markdown、Code 与 URL 四类解析；每次编辑产生新的不可变笔记版本， 旧版本不覆盖，因此「这条结论基于哪一版原文」永远问得出来。

为什么强调不可变版本 可变笔记会让证据对齐结果失效而不自知。保留版本之后，证据引用带版本号， 原文被改动时对齐关系会显式过期，而不是悄悄继续生效。

模型输出治理

AI Provider 被抽象成可插拔接口：线上接 Qwen / DashScope，测试与本地开发用 Mock。 这样评测链路、任务重试和异常分支都能在没有网络、不计费的情况下跑通。

  • Prompt 侧要求 JSON 输出，并在解析端做容错处理，不假设模型一定给出合法结构。
  • 解析结果统一过 Zod Schema 校验，不合格的结构直接拒绝，不落库。
  • 每次生成记录模型、Prompt 版本、输入引用与生成状态，出问题时能定位到具体一次调用。

证据门禁

对齐算法用 精确匹配 + 字符 trigram Jaccard 滑窗：从原文返回 Top 5 候选片段， 按相似度分档处理。

分值判定处理
≥ 85硬证据可以支撑理解验证题目
60 – 84软引用展示但标注不确定，需用户确认
< 60未对齐不得进入验证，可驳回

用户可以对齐结果做三种操作：确认、降级、驳回。门禁的价值不在于让模型少说话， 而在于让「没有依据的话」有明确的、可看见的去向。

可靠任务

学习卡生成、证据对齐、理解评估、来源解析四类任务都由基于 PostgreSQL 的 AI Worker 编排， 不额外引入消息中间件——数据库同时是队列和事实源，一致性边界更窄。

  • Skip Locked 取任务，多 worker 并行不互相阻塞。
  • lease token 标识一次执行的所有权，避免旧执行者写回结果。
  • 幂等检查 + 90s 执行超时 + 120s 悬挂回收，进程崩溃后任务能被重新捞起。
  • 指数退避、最多 3 次执行，关停时等待在途任务并优雅退出。

评估与边界

验证回答基于原文证据做结构化评估，验证事件、理解事件与动态复习计划在同一个事务里写入， 避免出现「状态更新了但事件丢了」。评测集为 20 篇文档 / 123 个内容块，带版本号， 改动对齐策略时能对比同一批数据。

治理上做了四件事：AI 调用同意门禁、PII 脱敏、调用审计，以及 URL 抓取的 SSRF 防护。

SSRF 防护 用户提交的 URL 由服务端抓取，如果不加约束，内网地址与元数据接口就成了可访问目标。 这里在解析前对协议、主机解析结果做校验，只允许公网 HTTP(S) 目标。
