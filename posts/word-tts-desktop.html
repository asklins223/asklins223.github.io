小猪 wordTTS 桌面配音工作台

老师手上的原始素材常常就是一张 Word 或 Excel。这个应用直接读 .docx / .xlsx，按文档结构核对条目、给不同角色配声部、 批量生成 MP3，可选地把验证过的音频再录进外部教学系统。任务状态、产物和恢复事实都留在本机， 关掉应用第二天接着做。当前版本 v3.2.9。

五段流程与题型解析

界面固定五个主阶段：导入文档 → 内容核对 → 配置中心 → 生成任务 → 交付中心， 交付阶段下面挂一个可选的「系统录入」。

解析支持八类题型的结构化识别与混合顺序还原：信息获取、听后选择、听后应答、课文跟读、 信息转述及询问、听后记录并转述信息、模仿朗读，以及走 Excel 模板的词汇。 识别只依据文档结构证据，文件名不作为证据——不然改个文件名解析结果就跟着变。

解析这块有回归基线：每次快照记下 git_commit、脏文件清单和每份文档的 sha256 与解析结果，改解析器时能对比出到底动了哪些题。

声部怎么分

w/W 与 m/M 标记分别落到可配置的默认女声／男声 （出厂是英语-Amanda 与英语-George），无标识内容默认女声，单词和例句始终女声。 另外几条例外容易踩水：

  • 题干角色用独立的「题干音色」，参数与正文声部分开配置。
  • 解析器主动判定为男声的条目，会覆盖「默认女声」这条规则。
  • Reporter:、Mr Yan: 这类通用角色按称谓自动归入男／女声，名字可在配置中心改。

语速、语调、音量支持 0–100 任意整数，输出固定 MP3，配置方案能存成预设复用。

全部生成后切割

默认生成方式是整批提交，再按安全停顿把长音频切回每段，提交次数远少于逐条请求。 边界无法确认时保留合并音频并报告异常，不静默伪造分段。 另一条路是逐条生成，两种都在交付中心里。

交付校验

能进交付列表的产物要同时满足：

  • 任务 READY 且 verified=true；
  • Artifact 与字节 Blob 两边都是 READY；
  • SHA256、大小、扩展名、MIME 事实一致，且类型是 tts-segment。

源文档和解析产物不会被伪装成音频混进交付；ZIP 打包要求全部父项 SUCCEEDED。 批量生成最常见的事故就是 200 条里混进 3 个空文件，校验放在交付这一关， 课堂上打开压缩包之前就能发现。

恢复、取消与不猜结果

断线恢复、暂停／恢复、取消、重试、对账这些动作不是前端自己判断的， 由服务端返回的 available_actions 投影授权，界面只渲染被允许的动作。 存在未决外部副作用时不自动重试。

RECONCILIATION_DISABLED 讯飞这条链路明确不提供供应商对账路径。既然问不到真实结果，就按「可重试」呈现， 不去猜那段音频到底生成成功了没有。

本机历史中心保留最近 20 个任务，可以重新查看、试听、下载或归档。 归档保留审计事实与产物文件，归档不等于物理删除。

架构与状态

后端是 FastAPI 单进程，由 Electron 主进程拉起，Renderer 不直连 HTTP， API、SSE 与产物流都走主进程转发。领域核心在 workflow/ 的 32 个模块里 （仓储、状态机、引擎、提供者、产物库、事件存储、恢复、调度、重试策略、垃圾回收、副作用日志等）， 旧模型到原子模型之间是一条追加式的旁路写入。

状态由五个正交维度组合派生，UI 不允许凭单个事件或计数判断终态。 数据落在数据目录里的 workflow.db：WAL、synchronous=FULL、 外键开启、写事务 BEGIN IMMEDIATE，跨进程用独占文件锁，文件 0600、目录 0700； 12 个迁移，迁移前自动备份。

本机服务的边界

后端只绑 127.0.0.1。往上有三层：Origin 守卫（不允许返回 403）、 非 /api/v1 的旧路径统一返回 410、能力令牌做常量时间比对。 写操作要求 X-Idempotency-Key，状态更新用 state_version 与 draft_revision 做乐观并发。SSE 要先换一张 60 秒的一次性票据， 支持 Last-Event-ID 续传。

接口契约以 contracts/openapi.yaml 为事实源，前端类型由它生成， check:contracts 会跑 lint、重新生成、diff 和 tsc。

讯飞那一侧

音频由讯飞配音生成，走的是浏览器自动化：可见窗口持久登录、单线程串行化调用、 签名与提交追踪。首次生成需要在那个窗口里登录一次，登录态存在本机持久化 profile。 构建和 CI 一律固定 WORDTTS_ENABLE_REAL_PROVIDER=0，真实账号 smoke 不进默认构建流，所以 CI 不会产生供应商副作用和费用。

分发与更新

macOS 与 Windows 安装包都由 GitHub Actions 构建，只有三个工作流， 且只在推送 v* 标签或手动派发时运行。版本号以 version.json 为唯一来源，构建前同步到 Electron 的 package.json、 package-lock.json 与 CHANGELOG。

平台做法
macOS.dmg，打开即用或拖入 Applications；签名与公证需要额外的证书环境变量
Windows自绘 HTML Setup.exe（独立 Electron 工程 + 惰性 7z payload），安装／更新／卸载共用一套界面
更新优先 .blockmap 差分下载，条件不满足回退全量；应用内版本中心检查 GitHub Releases

Windows 安装器先出界面、再按需解压 payload，避免长时间白屏。 安装包与更新都发布在仓库的 Releases 页面。

测试与发布闸门

Python 侧 56 个测试文件用标准库 unittest，Electron 侧 27 个用 node --test。另外有四个闸门脚本：本地确定性 2A 流程（含两种 schema profile， 不产生真实供应商副作用）、发布边界不变量（校验三处版本号一致）、 有界 FakeProvider 性能基线，以及子进程被杀后的恢复探针。

升级兼容

应用沿用原来 WordTTS 的用户数据目录、应用 ID 与环境变量，历史不会丢。 workflow.db 在用户数据目录里而不在 .app 内，覆盖安装不动它。 固定数据目录访问不到时应用会停止启动并提示，而不是退回一个空的默认目录。 旧版 JSON 与会话目录保留但不自动导入，要并入新工作台先跑 dry-run 再显式 apply。
