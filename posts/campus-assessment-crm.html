校园版英语听说测评与 CRM 后台

我在这份工作上写的第一个服务端，同时包含一个自己从表结构写到页面的 CRM 后台。 校园版和个人版的区别是节奏：一个班或一个学校在同一时间段一起交， 请求是成片涌进来的，不是零散发生的。

测评核心 API

服务端提供三块能力：AI 口语测评、数据上报、题型解析。接口按 RESTful 设计， 测评结果与上报数据落在 MySQL，热数据与状态放 Redis，耗时的工作丢进任务队列异步做。

  • 上报要能重复提交而不写脏数据，所以按提交标识做幂等。
  • 口语测评依赖外部能力，超时和失败要能重试，也要能明确告诉端上现在处于哪种状态。
  • 题型解析放在服务端统一实现，端上只拿结构化结果。

性能与稳定性

集中提交带来的问题都很具体：接口变慢、队列堆积、部分记录卡在中间状态。 处理方式是先看链路再改：接口侧看 SQL 与缓存命中，任务侧看消费速率与重试次数， 并发场景下把重复执行和竞态写入的地方逐个收口。

CRM 后台

后台是全栈做的。后端负责用户检索、服务商权限和业务数据 API； 前端用 Vue 2 + Vue Router + Element UI 写管理页面，表结构也参与了设计。

模块做了什么
用户检索多条件查询与分页，配合索引避免全表扫
服务商权限按服务商维度限定可见与可操作的数据范围
业务数据统计与明细接口，供管理端页面展示与导出

这类后台的价值不在页面多好看，而在运营和客服能自己查到答案， 不用每次把问题丢回给开发。
